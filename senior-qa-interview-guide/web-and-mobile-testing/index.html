Overview #

Web and mobile testing represents the most tangible layer of quality assurance — where users directly interact with your product. Senior QA engineers must demonstrate not just knowledge of test techniques, but the ability to think systematically about complex user flows across platforms, devices, network conditions, and edge cases.

This chapter covers 30 scenario-based questions that interviewers commonly use to assess a candidate's ability to:

  • Decompose complex features into testable components
  • Identify high-risk areas that demand deeper coverage
  • Think cross-platform (iOS, Android, Web, PWA)
  • Consider non-functional requirements (security, performance, accessibility)
  • Design concrete test cases rather than listing abstract topics
  • Communicate a structured approach under time pressure

The CROSS Framework for Scenario Questions

Use this framework to structure your answers:

C - Clarify: Ask scope questions (platform? user type? integrations?)
R - Risk:    Identify what could go wrong (data loss, security, UX)
O - Outline: Design test categories (functional, edge, NFR)
S - Specify: Give concrete test cases with steps and expected results
S - Summartic: Summarize coverage and mention automation strategy

Q1How would you test a login page? #

Objective

Demonstrate ability to decompose a seemingly simple feature into comprehensive test coverage spanning functional correctness, security hardening, accessibility, and cross-platform behavior.

Interview Answer

"A login page seems simple but is one of the highest-risk surfaces in any application. I'd structure my approach using risk-based thinking.

First, I'd clarify scope: What authentication methods are supported — email/password, SSO, OAuth, biometric? Is there MFA? What platforms — web, iOS, Android? Are there rate-limiting or lockout policies?

Risk identification: The login page is the front door for attackers. Top risks include credential stuffing, session hijacking, information disclosure through error messages, and broken accessibility preventing users from authenticating.

Test design — I'd organize into categories:

Functional (Happy Path):

  • Valid credentials → successful login → redirect to dashboard
  • 'Remember me' checkbox persists session across browser restarts
  • SSO redirect flow completes and maps to correct internal user

Functional (Negative):

  • Invalid password → generic error ('Invalid credentials' — not 'Wrong password')
  • Non-existent email → same generic error (prevents user enumeration)
  • Empty fields → client-side validation fires before network request
  • SQL injection in email field (' OR 1=1 --) → sanitized, no bypass
  • XSS payload in email field (<script>alert(1)</script>) → escaped in DOM

Security:

  • Credentials transmitted over HTTPS (inspect network tab for TLS)
  • Password field masked by default, with show/hide toggle
  • Session token is HttpOnly, Secure, SameSite=Strict
  • After 5 failed attempts → account lockout or CAPTCHA challenge
  • Concurrent sessions: login on Device B → behavior on Device A (configurable?)
  • CSRF token present in login form, validated server-side
  • Response timing is consistent for valid vs. invalid emails (prevents timing attacks)

Performance:

  • Login API responds < 500ms at P95 under normal load
  • Load test: 1000 concurrent login attempts → no degraded response
  • Third-party SSO provider timeout → graceful error message

Accessibility:

  • Form labels associated with inputs (for/id pairing)
  • Error messages announced by screen reader (aria-live region)
  • Tab order: email → password → remember me → login button
  • Sufficient color contrast on error states (4.5:1 ratio)
  • Login possible using keyboard only (Enter key submits form)

Platform-specific:

  • iOS: Keychain autofill prompt appears for saved credentials
  • Android: Autofill framework integration, biometric prompt if configured
  • Web: Password manager detection, autofill compatibility

I'd automate the functional and security regression tests in CI, use OWASP ZAP for periodic security scans, and run accessibility checks with axe-core in the pipeline."

Q2How would you test a chat application? #

Objective

Assess the candidate's ability to handle real-time systems with complex state management, concurrency, and multi-device synchronization challenges.

Interview Answer

"A chat application is one of the most complex features to test because it involves real-time communication, state synchronization, and numerous edge cases around connectivity. Let me walk through my approach.

Clarifying questions: Is this 1:1 chat, group chat, or both? What message types are supported — text, images, files, voice notes? Is there end-to-end encryption? What platforms — web, iOS, Android? Is there a message history limit?

Risk analysis: The top risks are message loss, message ordering, duplicate messages, sync failures across devices, and data leakage in group chats.

Test design:

Message Sending & Receiving:

  • Send text message → appears in recipient's chat within 2 seconds
  • Send message with emoji/unicode → renders correctly on all platforms
  • Send 10,000-character message → handled gracefully (truncated or scrollable)
  • Send message to offline user → delivered when they come online (with delivery indicator update)

Real-time Synchronization:

  • User A sends message while User B is typing → both messages appear in correct order
  • Open same conversation on phone and laptop → message appears on both simultaneously
  • Send message on phone, switch to web → message visible in web conversation

Group Chat Specifics:

  • Send message to 500-member group → all members receive within SLA
  • User removed from group → cannot see new messages, history behavior per spec
  • Admin deletes message → removed from all participants' views
  • @mention in group → notification only for mentioned user

Media Messages:

  • Send 25MB image → compression applied, preview generated, full-res downloadable
  • Send unsupported file type → clear error message, file not sent
  • Send image on poor connection → progress indicator, retry on failure
  • Video message → thumbnail generated, plays inline

Connectivity & Offline:

  • Send message while offline → queued with pending indicator
  • Reconnect after offline → queued messages sent in order
  • Switch from WiFi to cellular mid-conversation → no message loss
  • Server goes down mid-send → message retried with exponential backoff

Performance:

  • Scroll through 10,000 message history → smooth scrolling (virtualized list)
  • 100 messages received in burst → UI remains responsive
  • Chat with 1000 participants → member list loads progressively
  • Memory usage stays stable after 1 hour of active chatting

Security:

  • Messages encrypted in transit (TLS) and at rest
  • Cannot access other users' conversations via API manipulation
  • Deleted messages purged from server (not just hidden)
  • File attachments scanned for malware before delivery
  • Rate limiting on message sends (prevent spam)

Accessibility:

  • Screen reader announces new messages with sender name
  • Keyboard shortcut to send (Enter) and new line (Shift+Enter)
  • Message timestamps accessible to assistive technology
  • High contrast mode maintains readability"

Q3How would you test offline message sending? #

Objective

Evaluate the candidate's understanding of offline-first architecture, queue management, conflict resolution, and resilience testing techniques.

Interview Answer

"Offline message sending is a critical reliability feature. Users expect their messages to be delivered once connectivity resumes, without loss or duplication. Here's how I'd approach testing it.

Clarifying questions: What's the offline queue size limit? Is there a TTL on queued messages? How does the app indicate offline status? Does it support all message types offline (text, media, reactions)?

Risk analysis: Key risks are message loss, duplicate sends on reconnection, incorrect ordering, queue overflow, and poor UX (user doesn't realize they're offline).

Test design:

Basic Offline Queueing:

  • Enable airplane mode → send message → verify pending indicator shown
  • Send 5 messages offline → disable airplane mode → all 5 delivered in order
  • Verify messages appear in conversation immediately (optimistic UI) with pending state
  • Kill app while offline with queued messages → relaunch → messages still in queue

Queue Management:

  • Send 100 messages offline → verify queue doesn't corrupt or lose messages
  • Queue near capacity → send another → graceful handling (error or oldest evicted)
  • Mix message types offline: text, image, reply, reaction → all types queue correctly
  • Cancel a queued message before reconnection → message removed from queue

Reconnection Behavior:

  • Disable WiFi → send messages → enable WiFi → messages flush in FIFO order
  • Flapping connection (on/off/on rapidly) → no duplicates, no message loss
  • Reconnect to different network (WiFi → cellular) → queue flushes normally
  • Server returns 500 on first retry → exponential backoff, eventual delivery

Ordering & Timestamps:

  • Send 3 messages offline, recipient sends 2 messages during that time → correct interleaving on reconnection based on timestamps
  • Offline message timestamps reflect send-time (when user tapped send), not delivery-time
  • Verify server-side ordering uses client-provided timestamps for offline messages

Multi-device Conflict:

  • Send message offline on phone, same message sent from laptop (online) → no duplicate in conversation
  • Offline message from Device A, online message from Device B to same thread → both appear, correct order

Edge Cases:

  • Send message offline → manually change device time → reconnect → timestamp handling
  • Send offline → app update occurs before reconnection → messages still delivered
  • Low storage on device → offline queue persistence behavior
  • Send message offline to a user who blocked you during offline period → appropriate error on reconnection

Platform-specific:

  • iOS: Background app refresh + offline queue (app suspended vs. terminated)
  • Android: WorkManager/JobScheduler for queue flush on connectivity change
  • Web: Service Worker + IndexedDB queue persistence

Verification tooling:

  • Use Charles Proxy / mitmproxy to simulate network conditions
  • Use Xcode Network Link Conditioner for iOS
  • Android Emulator network throttling settings
  • Monitor local database/IndexedDB for queue state inspection"

Q4How would you validate ordering across reconnects? #

Objective

Test understanding of distributed systems concepts — causal ordering, vector clocks, sequence numbers — and how to verify correctness in chat/messaging systems.

Interview Answer

"Message ordering across reconnects is a subtle but critical problem. When a client disconnects and reconnects, it may receive a burst of messages that arrived during the offline period. The challenge is ensuring these messages appear in the correct order relative to each other and to any messages the user sent while offline.

Clarifying questions: What ordering guarantee does the system provide — causal, total, or best-effort? Are sequence numbers client-generated or server-assigned? Is ordering per-conversation or global? How are conflicts resolved?

Risk analysis: Incorrect ordering leads to confusing conversations (answers before questions), broken thread contexts, and potential data integrity issues in transactional systems.

Test design:

Basic Ordering Verification:

  • User A sends messages M1, M2, M3 sequentially → User B sees them in same order
  • User B is offline → M1, M2, M3 arrive → User B reconnects → sees M1, M2, M3 in order
  • Verify ordering uses server-assigned sequence numbers, not client timestamps (clocks drift)

Cross-user Ordering:

  • User A sends M1, User B sends M2, User A sends M3 (all while User C is offline) → User C reconnects and sees M1, M2, M3 in causal order
  • Two users send simultaneously in a group → server determines order, all clients see same order
  • Verify that the ordering is consistent across all group participants (total order)

Reconnection Burst Scenarios:

  • Client offline for 1 hour, 500 messages accumulated → on reconnect, all arrive in correct sequence
  • Client reconnects and receives batch → verify no UI flicker or reordering during render
  • Pagination of missed messages: first batch arrives, user scrolls, second batch arrives → no reorder

Network Partition Scenarios:

  • Client has intermittent connectivity (connected for 2s, disconnected for 5s, repeat) → messages from multiple gaps merge correctly
  • Client sends M1 offline, reconnects briefly (M1 sent), disconnects, sends M2 offline, reconnects → M1, M2 in order
  • Split-brain: two clients believe they're sending M3 → server resolves with tie-breaking rule

Clock Skew Testing:

  • Set device clock 5 minutes ahead → send message → verify server uses its own timestamp for ordering
  • Set device clock 1 hour behind → send message → message doesn't appear at bottom of old history
  • Two devices with 30-second clock difference → messages still ordered correctly

Sequence Number Validation:

  • Inspect sequence numbers in API response → strictly monotonically increasing per conversation
  • Gap in sequence numbers after reconnect → client requests missing messages
  • Duplicate sequence number received → client deduplicates (idempotent processing)

Stress & Concurrency:

  • 10 users sending messages simultaneously to one group → total order consistent for all
  • Reconnect during high-traffic burst (100 msg/sec in group) → no ordering violations
  • Database replication lag → verify read-your-own-writes consistency"

Q5How would you test duplicate-message prevention? #

Objective

Evaluate understanding of idempotency, client-side deduplication keys, server-side uniqueness constraints, and testing strategies for exactly-once delivery semantics.

Interview Answer

"Duplicate messages are one of the most common and annoying bugs in messaging systems. They typically occur during reconnection retries, double-tap on send, or server-side processing failures. Here's my testing approach.

Clarifying questions: Does the system use client-generated idempotency keys? Is deduplication handled client-side, server-side, or both? What's the dedup window (how long are IDs tracked)? Does it apply to all message types?

Risk analysis: Duplicates erode user trust, corrupt read counts, trigger duplicate notifications, and in transactional contexts (payments, orders) can cause real financial harm.

Test design:

Client-side Deduplication:

  • Rapidly tap send button 5 times → only 1 message appears in conversation
  • Send button disables after first tap (UI-level prevention)
  • Verify client generates unique idempotency key (UUID) per message intent
  • Resend same message text → different idempotency key → treated as new message (user intent)

Network Retry Deduplication:

  • Send message → simulate network timeout (server received but ACK lost) → client retries → only 1 message on server
  • Send message → server returns 500 → client retries with same idempotency key → server deduplicates
  • Send message → connection drops mid-request → reconnect → retry → no duplicate
  • Verify retry uses same idempotency key as original attempt

Reconnection Scenarios:

  • Client sends M1 offline → reconnects → flush sends M1 → ACK lost → second flush → still only 1 M1
  • WebSocket reconnect triggers re-send of unacknowledged messages → server deduplicates
  • Multiple reconnection cycles in quick succession → no duplicates

Server-side Verification:

  • Send message with duplicate idempotency key via API directly → server returns 200 (idempotent) but doesn't create second record
  • Query database directly: SELECT COUNT(*) FROM messages WHERE idempotency_key = X → always 1
  • Race condition: two requests with same key arrive simultaneously → exactly one stored (database constraint)

Edge Cases:

  • Idempotency key collision (UUID collision — theoretical) → verify handling
  • Dedup window expiry: send message, wait beyond dedup window, retry with same key → behavior defined (new message or still deduped?)
  • Client cache cleared → retry generates new idempotency key → potential duplicate (verify server-side protection)
  • Message edit vs. new message: editing a message should not be treated as duplicate of original

Multi-device Scenarios:

  • Same user sends same text from two devices simultaneously → two separate messages (different idempotency keys, different intent)
  • Offline queue synced from Device A, same queue somehow synced from Device B → server deduplicates by key

Automation Approach:

  • Intercept network at proxy level to simulate ACK loss
  • Inject duplicate API calls in integration tests
  • Monitor production for duplicate messages (alerting on same idempotency_key with multiple message_ids)"

Common Mistakes to Avoid

  1. Confusing identical content with duplicate messages — Same text ≠ duplicate; the idempotency key determines identity
  2. Testing only at UI level — Double-tap prevention is necessary but not sufficient; network retries need server-side dedup

OTP Generation & Delivery:

  • Request OTP → code received via SMS/email within 30 seconds
  • OTP is correct length (6 digits) and numeric
  • Each OTP request generates a different code (not predictable sequence)
  • Code delivered to correct phone/email (not leaked to other channels)
  • TOTP: authenticator app code matches server expectation within time window

OTP Validation:

  • Enter correct OTP → authentication succeeds, redirected to app
  • Enter incorrect OTP → error message, remaining attempts shown
  • Enter expired OTP (after TTL) → "Code expired, request new one" message
  • Enter OTP from previous session → rejected (not replayable)

  • Copy-paste OTP → works correctly (no formatting issues)

Rate Limiting & Brute Force:

  • Enter wrong OTP 5 times → account locked or extended cooldown
  • Request OTP 10 times rapidly → rate limited after threshold (e.g., 3 per 10 min)
  • After lockout → legitimate user can still recover via backup method
  • Brute force attempt via API (scripted) → blocked by rate limiting + CAPTCHA

Timing & Expiration:

  • OTP valid for exactly 5 minutes (or configured TTL)
  • Enter OTP at 4:59 → accepted; at 5:01 → rejected
  • TOTP: code valid for current 30s window + 1 previous window (clock skew tolerance)
  • Time-of-check vs time-of-use: verify OTP can't be used in the microsecond after expiry

Fallback & Recovery:

  • Primary method fails (SMS not delivered) → option to use backup method
  • Backup codes: each code usable exactly once, then invalidated
  • Lost device → recovery flow (support ticket, identity verification)
  • All MFA methods lost → account recovery process (security questions, ID verification)

  • OTP entered on different device than where it was requested → behavior defined
  • Request OTP on web, enter on mobile (cross-device flow) → works if same session context
  • Multiple browser tabs: request OTP in Tab A, enter in Tab B → last OTP valid

  • Man-in-the-middle: phishing site proxies OTP to real site → FIDO2/WebAuthn immune

Objective

Evaluate understanding of security mechanism testing, including the balance between protecting against brute force and not creating denial-of-service for legitimate users.

Interview Answer

"Account lockout is a double-edged sword — it protects against brute force but can itself become a denial-of-service vector if an attacker intentionally locks out legitimate users. I'd test both the security efficacy and the usability impact.

Test design:

Threshold Testing:

  • Enter wrong password N-1 times → account still active, warning shown ("1 attempt remaining")
  • Enter wrong password N times → account locked, clear message shown
  • Enter correct password after lock → still locked (credentials not checked during lockout)
  • Verify threshold is per-account, not per-session (closing browser doesn't reset counter)
  • Mixed case: 3 wrong attempts, 1 correct, 2 more wrong → counter behavior (reset on success?)

Lockout Duration & Recovery:

  • Temporary lockout: verify account unlocks after specified duration (e.g., 30 minutes)
  • Try login at 29 minutes → still locked; at 31 minutes → unlocked
  • Permanent lockout: verify only admin or self-service flow can unlock
  • Self-service unlock via email/SMS verification → works, counter resets
  • After unlock, user can login with correct credentials immediately

Progressive Delay (if implemented instead of hard lockout):

  • 1st failure: no delay; 3rd failure: 5s delay; 5th failure: 30s delay; 10th: 5min
  • Verify delay is enforced server-side (not just UI), API returns 429
  • After successful login, delay counter resets

Notification & Awareness:

  • Account locked → email notification sent to account owner ("Suspicious activity detected")
  • Email includes: time, IP address, location (if available), unlock instructions
  • Multiple lockouts → escalation (additional verification required on unlock)
  • Admin dashboard shows locked accounts with attempt details

Attack Scenarios:

  • Brute force from single IP → locked + IP temporarily blocked
  • Distributed brute force (different IPs, same account) → account-level protection triggers
  • Account lockout DoS: attacker locks victim's account intentionally → victim has self-service unlock
  • Credential stuffing (valid emails, random passwords) → global rate limiting across accounts
  • Username enumeration via lockout: locked vs. non-existent account → same response (no info leak)

Boundary & Integration:

  • Lockout applies to all login paths: web, mobile app, API, SSO
  • OAuth/SSO login attempts → do they count against lockout? (usually no, external IDP handles)
  • Password change during lockout period → behavior defined (usually not possible)
  • Admin manually unlocking account → immediate effect, user can login
  • Lockout state survives server restart (persisted, not in-memory only)

Monitoring & Alerting:

  • Spike in lockouts → security team alerted (potential attack)
  • Lockout metrics visible in dashboard (locked accounts count, trend)
  • Audit log captures all lockout events with context"

  • Click "Forgot password" → enter email → receive reset link within 60 seconds
  • Click link → enter new password → confirm → password updated
  • Login with new password → success
  • Old password no longer works

Token Security:

  • Reset token is cryptographically random (not sequential, not predictable)
  • Token is minimum 128 bits of entropy (32+ hex characters)
  • Token expires after configured time (e.g., 1 hour)
  • Token is single-use (clicking link twice → second time shows "Link expired")
  • Token is invalidated if user requests a new reset link
  • Token is invalidated after successful password change
  • Token in URL → verify no referrer leakage (Referrer-Policy: no-referrer on reset page)

Email/User Enumeration Prevention:

  • Enter registered email → "If an account exists, we sent a reset link" (generic)
  • Enter non-existent email → same message (no "Email not found" error)
  • Response timing consistent for both cases (prevent timing attacks)

Password Requirements:

  • New password must meet complexity requirements (shown clearly)
  • New password cannot be same as current/previous N passwords
  • Password strength meter provides real-time feedback
  • Confirm password field must match
  • Common/breached passwords rejected (haveibeenpwned check)

Session & Security Impact:

  • After password reset → all existing sessions invalidated (force re-login everywhere)
  • Active sessions on other devices terminated immediately
  • Notification email sent: "Your password was changed" (to detect unauthorized reset)
  • If user didn't initiate reset → "secure your account" link in notification

Rate Limiting:

  • Request reset 10 times for same email → rate limited after 3 (prevent email bombing)
  • Request reset for many different emails from same IP → blocked (credential stuffing)
  • Rate limiting doesn't reveal which emails exist

Edge Cases:

  • Request reset → change email address before clicking link → token invalidated
  • Request reset → account disabled by admin → token invalid
  • Multiple pending reset tokens → only latest should work
  • Reset link opened in different browser/device → should still work (token-based, not session-based)
  • Reset link with modified email parameter → rejected (token bound to specific email)
  • Password reset for OAuth-only account → "Use Google/SSO to sign in" message

Platform-specific:

  • iOS: Universal link opens app to reset screen (not Safari)
  • Android: Deep link opens app to reset screen
  • Email client: link renders correctly in Gmail, Outlook, Apple Mail
  • Mobile: reset form usable on small screen, password field with show toggle"

Objective

Interview Answer

Test design:

Direct Upgrade (N to N+1):

  • Install previous version → add data (login, create content, save preferences) → upgrade → all data intact
  • Verify database schema migration runs successfully (no corruption)
  • Verify cached data (images, files) survives or is properly invalidated
  • Verify auth token remains valid (user stays logged in)
  • First launch after upgrade: no crash, no ANR, reasonable startup time

Skip-version Upgrade (N to N+3):

  • Install version 2.0 → add data → upgrade directly to 5.0 → verify migration chain works
  • Database migrations must be sequential and idempotent (2→3→4→5)
  • Test the longest realistic skip (based on analytics of update frequency)

Fresh Install vs. Upgrade:

  • Fresh install of latest version → compare behavior with upgraded version
  • Verify no "ghost data" from previous versions causing issues
  • Onboarding: fresh install shows tutorial; upgrade does not (or shows "what's new")

Data Migration:

  • Verify all user data persists: login state, preferences, drafts, downloads
  • Verify data format changes handled: e.g., date format changed, old dates migrated
  • Large local database (10,000 records) → migration completes without timeout
  • Encryption key rotation during upgrade → data re-encrypted successfully

API Backward Compatibility:

  • New server deployed → old app version still functions (API versioning)
  • Old server (during rollback) → new app version handles gracefully
  • Deprecated API endpoints → old client gets appropriate response (not 404)
  • New required field in API response → old client ignores it (doesn't crash)
  • Removed field from API response → new client handles absence gracefully

Rollback & Downgrade:

  • User downgrades app (uncommon but possible on Android) → app handles newer DB schema
  • Server rollback to previous version → current clients still work
  • Feature flag turns off new feature → app degrades gracefully to old behavior

Platform-specific Upgrade:

  • iOS: TestFlight beta → App Store release upgrade path
  • iOS: Background app refresh after update (silent migration)
  • Android: Auto-update at night → user opens to new version next morning
  • Android: In-app update (flexible vs. immediate) flow tested

Forced Update:

  • App version below minimum → forced update screen shown
  • Forced update screen: no way to dismiss, clear instructions to update
  • Verify minimum version endpoint is checked on app launch
  • Network failure during version check → grace period or cached decision

Coexistence Testing:

  • User A on v4, User B on v5, both in same chat → messages compatible

Q21How would you test session expiry? #

Objective

Evaluate understanding of session management, token lifecycle, graceful expiration handling, and security implications of session policies.

Interview Answer

"Session expiry is a security mechanism that must be invisible when working correctly but graceful when triggered. Users should never lose work, and the transition to re-authentication must be smooth. I'd test both the security enforcement and the user experience.

Clarifying questions: What's the session duration (idle timeout vs. absolute timeout)? Is there token refresh? What triggers expiry — inactivity, absolute time, or both? What happens to in-progress work? Are there different policies for different security levels?

Risk analysis: Sessions that never expire are security vulnerabilities, abrupt expiry causes data loss, inconsistent expiry across tabs/devices confuses users, and expired tokens not properly rejected create authorization bypass.

Test design:

Idle Timeout:

  • Stay inactive for timeout duration → session expires, redirect to login
  • Activity resets the timer (click, scroll, type) → session extends
  • Activity in one tab → all tabs stay alive (shared session heartbeat)
  • Inactive for timeout-1 minute → activity → session continues normally
  • Warning shown 5 minutes before expiry ("Your session expires soon. Click to extend.")

Absolute Timeout:

  • Login → regardless of activity, session expires after absolute duration (e.g., 8 hours)
  • Verify absolute timeout cannot be extended by activity (security policy for sensitive apps)
  • Banking context: 15-minute absolute timeout regardless of clicks

Token Refresh:

  • Access token expires → refresh token silently obtains new access token (no user disruption)
  • Refresh token expires → user must re-authenticate
  • API call with expired access token during refresh → queued and retried after refresh
  • Refresh token stolen → rotation mechanism invalidates old refresh token

Graceful Expiration UX:

  • Session expires during form entry → work saved locally, restored after re-login
  • Session expires during file upload → upload paused, resumed after re-login (or lost gracefully)
  • Session expires with unsaved changes → prompt to save before redirect
  • Warning modal: "Extend session" button works, "Log out" button works
  • Warning modal countdown timer accurate

API-level Enforcement:

  • Expired session token sent to API → 401 Unauthorized (not 500 or success)
  • All API endpoints check session validity (no unprotected endpoints)
  • Expired token cannot access any resource (test multiple endpoints)
  • Tampered token (modified payload) → rejected immediately

Multi-tab / Multi-device:

  • Login on two tabs → expire session → both tabs redirect to login
  • Login on browser + mobile → expire on server → both clients detect and redirect
  • Logout in one tab → all tabs redirect to login (session invalidation propagation)
  • Browser stores expired token in cookie → verify server rejects on next request

Edge Cases:

  • System clock change → session expiry based on server time, not client time
  • Device sleeps (laptop lid close) for hours → wake up → session expired gracefully
  • Slow network: session expires, user clicks button → loading then redirect (not infinite spinner)
  • Back button after session expiry → cannot access cached authenticated pages
  • Session expires during OAuth flow → restart flow cleanly"

Q22How would you test user permissions? #

Objective

Assess ability to test authorization (not authentication), role-based access control (RBAC), attribute-based access control (ABAC), and the principle of least privilege across UI and API layers.

Interview Answer

"Permissions testing ensures users can only access what they're authorized to. I'd test both that authorized users CAN access resources and that unauthorized users CANNOT — at both UI and API levels.

Clarifying questions: What permission model — RBAC, ABAC, or custom? What roles exist (admin, manager, member, viewer)? Can permissions be customized per resource? Are permissions inherited (org → team → project)? Is there a super-admin/bypass role?

Risk analysis: Unauthorized data access (data breach), privilege escalation (user gains admin), horizontal privilege violation (user A accesses user B's data), and UI-only restrictions without API enforcement (bypassable).

Test design:

Role-Based Access (Vertical):

  • Admin role → can access all features (user management, billing, settings)
  • Member role → cannot access admin features (menu items hidden + API returns 403)
  • Viewer role → can read but not write/edit/delete
  • Each role tested against every feature → permission matrix verified
  • New feature added → verify it's restricted to appropriate roles by default

Horizontal Access Control:

  • User A accesses their own data → success
  • User A modifies API request to access User B's data → 403 (not 404 — debatable)
  • User A's list endpoint only returns their own resources (no data from other users)
  • Shared resource: User A shares with User B → B can access; User C cannot

UI vs. API Enforcement:

  • Restricted feature: button hidden in UI → also returns 403 from API
  • Verify you cannot bypass UI restrictions by calling the API directly
  • Test with curl/Postman using the user's token against restricted endpoints
  • Disabled buttons in UI → verify the action is also server-side rejected

Permission Changes (Dynamic):

  • Admin removes user's permission → immediate effect (next request rejected)
  • User upgraded from Member to Admin → new features available immediately
  • Permission revoked while user is actively using feature → current session behavior
  • Team membership removed → all team resources inaccessible

Inheritance & Hierarchy:

  • Org admin → automatically has admin on all teams within org
  • Team permission doesn't grant org-level access
  • Project-level permission overrides team-level (if applicable)
  • Removing parent permission cascades to children

Permission Boundaries:

  • Viewer can't delete resources (UI hides button AND API rejects)
  • Member can't invite users (if that's admin-only)
  • User can't elevate their own permissions (even through API)
  • Non-owner can't transfer ownership
  • Deactivated user's token immediately rejected

Edge Cases:

  • User with multiple roles → effective permission is union (or most permissive)
  • Last admin leaves team → system prevents removal (at least one admin required)
  • User's role changed while they have pending actions → actions validated at execution time
  • Permission for resource that doesn't exist → 404 (not 403, avoid revealing existence)
  • Concurrent permission check: permission revoked at same millisecond as API call → consistent result

Automation Strategy:

  • Build permission matrix test: iterate all roles × all endpoints × all methods
  • Run as integration tests: create users with each role, attempt all actions
  • Flag any endpoint without authorization check (security audit tool)"

Q23How would you test a feature flag? #

Objective

Demonstrate understanding of feature flag lifecycle, testing flag states independently, gradual rollouts, and the complexity of flag-dependent interactions.

Interview Answer

"Feature flags add a dimension to testing — every feature now has multiple states, and the flag system itself needs testing. I'd approach this by testing the flag mechanism, each feature state, and the transitions between states.

Clarifying questions: What flag system is used (LaunchDarkly, Split, custom)? What targeting rules — percentage, user segment, geography? Kill switch capabilities? How are flags managed (dashboard, config file, API)? What's the flag cleanup strategy?

Risk analysis: Flag misconfiguration exposing unfinished features, flags creating inconsistent state for users, stale flags accumulating technical debt, flag-dependent code paths untested, and flag evaluation performance impact.

Test design:

Basic Flag States:

  • Flag ON → feature visible and functional
  • Flag OFF → feature hidden, no traces in UI, no API endpoints exposed
  • Flag default (no explicit value) → falls back to defined default (usually OFF)
  • Flag deleted from system → code uses hardcoded default, no crash

Targeting Rules:

  • Flag ON for 10% of users → verify approximately 10% see it (statistical test)
  • Flag ON for specific user segment (beta users) → beta users see it, others don't
  • Flag ON for geographic region (US only) → US users see it, EU users don't
  • Flag ON for specific user IDs → only those IDs affected
  • User moves between segments → flag state updates accordingly

Rollout Progression:

  • 1% → verify no errors/crashes at scale
  • 10% → monitor error rates, verify feature works
  • 50% → load test at half capacity
  • 100% → full rollout, final verification
  • At each stage: performance metrics, error rates, user feedback

Kill Switch (Emergency OFF):

  • Feature causing errors → toggle flag OFF → feature immediately disappears
  • Verify kill switch takes effect within seconds (not cached for hours)
  • Verify users mid-flow when flag toggles → graceful handling (not crash)
  • After kill switch: verify no partial state left (e.g., half-processed data)

Flag Interactions:

  • Flag A and Flag B both ON → test combined behavior (feature interactions)
  • Flag A ON, dependency Flag B OFF → verify graceful fallback
  • Multiple flags controlling same feature (override logic) → priority defined and tested
  • Flag controlling flag evaluation (meta-flags) → tested at all levels

Code Path Testing:

  • Verify both code paths (flag ON and OFF) have test coverage
  • No dead code when flag is permanently ON (cleanup verification)
  • Flag evaluation doesn't cause performance issues (evaluated per request? cached?)
  • Flag evaluation failures (service down) → fallback to safe default

Consistency:

  • Same user always sees same flag state within a session (sticky bucketing)
  • Flag state doesn't change mid-flow (e.g., start checkout with new UI, finish with new UI)
  • Logged out → logged in: flag state transfers correctly
  • Multiple devices: flag state consistent for same user

Testing Approach:

  • Unit tests: force flag value, test both code paths
  • Integration tests: test with real flag service, verify targeting
  • Staging environment mirrors production flag configuration
  • Monitor: flag evaluation metrics, error rates per flag state"

Objective

Interview Answer

"Deletion testing is more complex than it appears — data exists in multiple places (databases, caches, backups, search indexes, CDNs), and regulatory requirements demand different behaviors for different data types. I'd test both the user-facing deletion and the backend completeness.

User-initiated Deletion:

  • Delete a message → message disappears from sender's view
  • Delete a message → behavior for recipients (still visible? "Deleted message" placeholder?)
  • Delete all data (account deletion) → confirmation prompt with consequences explained
  • Undo period: within 30 seconds → undo successful, data restored
  • After undo period → data removed from view, enters retention period

Soft Delete & Recovery:

  • Deleted item moves to "Trash" / "Recently Deleted"
  • Item in trash still counts against storage? (product decision)
  • Recover from trash → item fully restored to original location
  • Trash auto-empties after retention period (e.g., 30 days)
  • Admin can recover items during retention period (support use case)

Hard Delete (Permanent):

  • After retention period → data permanently removed from primary database
  • Verify: direct database query returns no record (not just flagged)
  • Search index updated → deleted content not searchable
  • CDN cache purged → media files not accessible via direct URL
  • Backup retention: data exists in backups for X days (compliance documentation)

Cascading Effects:

  • Delete user → what happens to their content in shared spaces?
  • Delete conversation → all messages deleted? Or just membership removed?
  • Delete parent resource → child resources cascade deleted (with confirmation)
  • Delete file → all references/previews/thumbnails also cleaned up

GDPR Right to Erasure (Article 17):

  • User requests data deletion → processed within 30 days
  • Deletion scope: all personal data across all systems
  • Third-party data sharing: notify partners to delete (documented)
  • Exceptions: data required for legal obligation retained with justification
  • Deletion certificate/confirmation provided to user

Retention Policies:

  • Data type A retained for 7 years (financial regulations)
  • Data type B retained for 90 days (analytics)
  • Data type C deleted immediately on request (personal messages)
  • Automated enforcement: verify scheduled jobs actually delete on time
  • Retention policy displayed to users (transparency)

Multi-location Verification:

  • Primary database: record deleted ✓
  • Read replicas: propagation within replication lag window ✓
  • Elasticsearch/search index: removed from search results ✓
  • Redis/cache: evicted or invalidated ✓
  • CDN: purge sent, asset returns 404 ✓
  • Data warehouse: anonymized or deleted per retention ✓
  • Audit logs: maintain who deleted, but content redacted ✓

Edge Cases:

  • Delete data referenced by other users (tagged in photo, mentioned in comment)
  • Delete during ongoing export/download → export doesn't include deleted data
  • Delete data that's currently being processed by async job
  • Bulk delete (10,000 records) → completes without timeout, rate limited if needed

WCAG Regression Checklist (Per Component):
  ☐ Keyboard navigable (Tab, Enter, Escape, Arrow keys)
  ☐ Focus visible and logically ordered
  ☐ Screen reader announces role, name, value, state
  ☐ Color contrast meets AA (4.5:1 text, 3:1 UI)
  ☐ Color not sole differentiator
  ☐ Resizable to 200% without loss
  ☐ Motion reducible (prefers-reduced-motion)
  ☐ Labels and errors programmatically associated
  ☐ Dynamic changes announced (aria-live)
  ☐ No keyboard traps

Common Mistakes to Avoid

  1. Relying solely on automated scanning — Automated tools catch ~30-40% of issues; manual testing is essential
  2. Testing only with keyboard — Keyboard alone doesn't verify screen reader announcements
  3. Checking accessibility once, not continuously — Accessibility regresses with every code change
  4. Ignoring dynamic content — Modals, live updates, and AJAX content need special ARIA handling
  5. Treating accessibility as a QA-only concern — It starts at design and development; QA verifies

Chapter Summary #

Key Themes Across All 30 Questions

  1. The CROSS Framework applies to every scenario question: Clarify scope → identify Risks → Outline test categories → Specify concrete cases → Summarize with automation strategy.

  2. Multi-layer thinking is essential: UI testing alone is never sufficient. Every scenario requires testing at API level, database level, and across network conditions.

  3. Platform awareness differentiates senior candidates: Understanding iOS vs. Android vs. Web differences in lifecycle, permissions, storage, and user expectations.

  4. Security is always relevant: Whether testing a chat app or a dark mode toggle, senior engineers identify security implications (injection, access control, data exposure).

  5. Accessibility is non-negotiable: Every user-facing feature must be keyboard navigable, screen reader compatible, and meet contrast requirements.

  6. Performance degrades at scale: Features that work with 10 items break with 10,000. Senior engineers test at realistic scale.

Interview Success Patterns

What distinguishes a senior answer:

  • Opens with clarifying questions (shows real-world experience)
  • Identifies 3-5 specific risk areas before diving into test cases
  • Provides concrete test cases with specific steps and expected results
  • Covers functional, security, performance, and accessibility dimensions
  • Mentions automation strategy and CI/CD integration
  • Acknowledges platform differences where relevant
  • Closes with what they'd monitor in production

What to avoid:

  • Generic answers ("I'd test positive and negative cases")
  • Only listing test categories without specific cases
  • Ignoring security or accessibility entirely
  • Not mentioning automation or CI/CD
  • Platform-agnostic answers for platform-specific questions
  • Not asking clarifying questions (assumes one-size-fits-all)

Preparing for Your Interview

  1. Practice the CROSS framework on each question until it's natural (< 30 seconds to set up)
  2. Memorize 3-5 concrete test cases per question type (specificity impresses)
  3. Have platform-specific examples ready — iOS/Android/Web differences show depth
  4. Know your tools — mention specific tools you've used (axe-core, k6, Charles Proxy)
  5. Connect testing to business impact — "This test prevents revenue loss because..."
  6. Practice timing — Interview answers should be 2-3 minutes, not 10 minutes
