Q1What makes an API idempotent? #

Objective

Demonstrate understanding of idempotency as a distributed systems concept and explain how it impacts API design and testing strategy.

Interview Answer

An API operation is idempotent when making the same request multiple times produces the same result as making it once. The server state does not change after the first successful execution, regardless of how many times the client repeats the call.

HTTP Method Idempotency by Specification:

  • GET, PUT, DELETE, HEAD, OPTIONS — idempotent by design
  • POST — NOT idempotent by default (requires explicit implementation)
  • PATCH — NOT guaranteed idempotent

For POST operations (e.g., creating a payment), idempotency is achieved through an idempotency key — a unique client-generated identifier sent in a header. The server stores this key with the response and returns the cached result on subsequent calls.

Why it matters for QA:

  1. Network failures cause retries — without idempotency, a payment could be charged twice
  2. Load balancers may replay requests during failover
  3. Message queues may deliver the same message multiple times (at-least-once delivery)
// REST Assured — Testing PUT idempotency
@Test
public void testPutIdempotency() {
    String payload = "{\"name\": \"Updated User\", \"email\": \"user@test.com\"}";

    // First PUT request
    Response first = given()
        .header("Content-Type", "application/json")
        .body(payload)
    .when()
        .put("/api/v1/users/123")
    .then()
        .statusCode(200)
        .extract().response();

    // Second identical PUT request
    Response second = given()
        .header("Content-Type", "application/json")
        .body(payload)
    .when()
        .put("/api/v1/users/123")
    .then()
        .statusCode(200)
        .extract().response();

    // Both responses should be identical
    assertEquals(first.jsonPath().getString("name"), second.jsonPath().getString("name"));
    assertEquals(first.jsonPath().getString("updatedAt"), second.jsonPath().getString("updatedAt"));
}

Common Mistakes to Avoid

  • Assuming all DELETE operations are idempotent (some return 404 on second call vs 204)
  • Confusing idempotent with safe (PUT is idempotent but not safe — it modifies state)
  • Not testing the database state after repeated calls (response may look same but DB has duplicates)

  • What happens if a network timeout occurs between the server processing and sending the response?

Q2How would you test idempotency keys? #

Objective

Show practical test design for validating idempotency key implementations in payment or order creation APIs.

Interview Answer

An idempotency key is a unique value (typically UUID) sent by the client in a request header. The server uses this key to detect duplicate requests and return the original response without re-executing the operation.

Test Strategy for Idempotency Keys:

  1. Happy path — Same key, same request returns cached response
  2. Same key, different body — Should return 422 Unprocessable Entity
  3. Key expiration — After TTL, key should no longer be recognized
  4. Concurrent requests — Same key sent simultaneously should process only once
  5. Different keys, same body — Should create two separate resources
// REST Assured — Comprehensive idempotency key testing
@Test
public void testIdempotencyKey_duplicateRequest_returnsCachedResponse() {
    String idempotencyKey = UUID.randomUUID().toString();
    String payload = "{\"amount\": 5000, \"currency\": \"USD\", \"recipient\": \"acc_123\"}";

    // First request — creates the payment
    Response first = given()
        .header("Content-Type", "application/json")
        .header("Idempotency-Key", idempotencyKey)
        .header("Authorization", "Bearer sk_test_token")
        .body(payload)
    .when()
        .post("/api/v1/payments")
    .then()
        .statusCode(201)
        .extract().response();

    // Second request — same key, same body
    Response second = given()
        .header("Content-Type", "application/json")
        .header("Idempotency-Key", idempotencyKey)
        .header("Authorization", "Bearer sk_test_token")
        .body(payload)
    .when()
        .post("/api/v1/payments")
    .then()
        .statusCode(200) // Note: 200 not 201 — indicates cached
        .extract().response();

    assertEquals(first.jsonPath().getString("id"), second.jsonPath().getString("id"));
    assertEquals(first.jsonPath().getInt("amount"), second.jsonPath().getInt("amount"));
}

@Test
public void testIdempotencyKey_sameKeyDifferentBody_returnsConflict() {

    .when()
        .post("/api/v1/payments")
    .then()

Q3What is a correlation ID and how do you use it? #

Objective

Explain how correlation IDs enable distributed tracing and how QA leverages them for debugging cross-service issues.

Interview Answer

A correlation ID (also called trace ID or request ID) is a unique identifier attached to a request that propagates across all services involved in processing that request. It creates a thread linking logs, metrics, and traces across the entire request lifecycle.

How it works:

  1. Client or API gateway generates a UUID and attaches it as a header (e.g., X-Correlation-ID)
  2. Each downstream service reads and forwards this header
  3. Every log entry includes the correlation ID
  4. When an issue occurs, you search logs by correlation ID to see the full journey

QA uses correlation IDs to:

  • Trace a failed request through multiple services
  • Verify that all services in a chain received and processed the request
  • Identify which service introduced latency or errors
  • Validate that logs are properly correlated in observability platforms
// REST Assured — Testing correlation ID propagation
@Test
public void testCorrelationId_propagatedInResponse() {
    String correlationId = UUID.randomUUID().toString();

    given()
        .header("X-Correlation-ID", correlationId)
        .header("Authorization", "Bearer token123")
    .when()
        .get("/api/v1/orders/456")
    .then()
        .statusCode(200)
        .header("X-Correlation-ID", equalTo(correlationId));
}

@Test
public void testCorrelationId_generatedWhenMissing() {
    Response response = given()
        .header("Authorization", "Bearer token123")
    .when()
        .get("/api/v1/orders/456")
    .then()
        .statusCode(200)
        .extract().response();

    String generatedId = response.getHeader("X-Correlation-ID");
    assertNotNull(generatedId, "Server should generate correlation ID if not provided");
    assertTrue(generatedId.matches("[0-9a-f\\-]{36}"), "Should be valid UUID format");
}

}

Common Mistakes to Avoid

  • Not verifying that correlation IDs appear in error response bodies (not just headers)
  • Assuming the client must always provide the ID (server should generate if missing)
  • Not checking that downstream services actually propagate the ID (integration gap)
  • Confusing correlation ID with session ID or request ID (different scopes)

Q4How do you test a timeout followed by retry? #

Objective

Demonstrate ability to validate retry logic and timeout handling in distributed systems, including exponential backoff verification.

Interview Answer

Testing timeout-then-retry scenarios validates that the system gracefully handles slow or unresponsive dependencies. The key is to simulate controlled delays, verify retry behavior, and ensure no duplicate side effects.

Test Strategy:

  1. Use WireMock or a mock server to introduce artificial delays
  2. Verify the client retries with correct backoff intervals
  3. Confirm that the final response is correct after recovery
  4. Validate that retries don't cause duplicate operations
  5. Check circuit breaker activation after max retries
// WireMock + REST Assured — Testing timeout and retry
@Test
public void testTimeout_retriesWithExponentialBackoff() {
    // First call — times out (delay > client timeout)
    stubFor(get(urlEqualTo("/api/v1/inventory/item/99"))
        .inScenario("Retry Test")
        .whenScenarioStateIs(Scenario.STARTED)
        .willReturn(aResponse()
            .withFixedDelay(5000) // 5s delay, client timeout is 3s
            .withStatus(200)
            .withBody("{\"stock\": 50}"))
        .willSetStateTo("FIRST_TIMEOUT"));

    // Second call — also times out
    stubFor(get(urlEqualTo("/api/v1/inventory/item/99"))
        .inScenario("Retry Test")
        .whenScenarioStateIs("FIRST_TIMEOUT")
        .willReturn(aResponse()
            .withFixedDelay(5000)
            .withStatus(200))
        .willSetStateTo("SECOND_TIMEOUT"));

    // Third call — succeeds
    stubFor(get(urlEqualTo("/api/v1/inventory/item/99"))
        .inScenario("Retry Test")
        .whenScenarioStateIs("SECOND_TIMEOUT")
        .willReturn(aResponse()
            .withFixedDelay(100) // Fast response
            .withStatus(200)
            .withBody("{\"stock\": 50}")));

    // Execute — the client should retry and eventually succeed
    long startTime = System.currentTimeMillis();

    Response response = given()
        .header("Authorization", "Bearer token")
    .when()
        .get("/api/v1/inventory/item/99")
    .then()
        .statusCode(200)
        .extract().response();

    long elapsed = System.currentTimeMillis() - startTime;

    assertEquals(50, response.jsonPath().getInt("stock"));
    // Verify exponential backoff: ~1s + ~2s + response time
    assertTrue(elapsed > 3000, "Should show backoff delay");

    // Verify exactly 3 attempts were made
    verify(3, getRequestedFor(urlEqualTo("/api/v1/inventory/item/99")));
}

@Test
public void testTimeout_maxRetriesExhausted_returns503() {
    // All calls timeout
    stubFor(get(urlEqualTo("/api/v1/inventory/item/99"))
        .willReturn(aResponse().withFixedDelay(10000).withStatus(200)));

    given()
        .header("Authorization", "Bearer token")
    .when()
        .get("/api/v1/inventory/item/99")
    .then()
        .statusCode(503)
        .body("error.code", equalTo("service_unavailable"))
        .body("error.message", containsString("retry"));
}
# curl — Testing with explicit timeout
curl -X GET https://api.example.com/v1/inventory/item/99 \
  -H "Authorization: Bearer token" \
  --connect-timeout 3 \
  --max-time 5 \
  -w "\nTime: %{time_total}s\nHTTP Code: %{http_code}\n"

Expected Retry Pattern:

Attempt 1: t=0s     → Timeout at 3s
Attempt 2: t=4s     → Timeout at 7s  (1s backoff)
Attempt 3: t=9s     → Timeout at 12s (2s backoff)
Attempt 4: t=13s    → Success or 503 (4s backoff, max retries)

Common Mistakes to Avoid

  • Not verifying the backoff intervals (just checking retries happened)
  • Forgetting to test the "all retries exhausted" scenario
  • Not checking for duplicate side effects (e.g., double charges after retry)
  • Not testing with jitter (real backoff includes randomization)

Follow-up Questions

  • How does exponential backoff with jitter prevent thundering herd?
  • What is the difference between connection timeout and read timeout?
  • How do you test retry behavior in message queue consumers?

Q5How do you test duplicate webhooks? #

Objective

Show how to validate that webhook consumers handle duplicate deliveries gracefully without processing the event twice.

Interview Answer

Webhook providers often send the same event multiple times due to network issues, retries, or infrastructure restarts. Testing duplicate webhook handling ensures the consumer is idempotent and deduplicates based on event ID.

Test Strategy:

  1. Send the same webhook payload twice with the same event ID
  2. Verify the side effect occurs only once
  3. Verify the second delivery returns 200 (acknowledged) without re-processing
  4. Test with slight variations in delivery timing (immediate vs delayed duplicate)
  5. Validate deduplication storage (Redis/DB) is correctly populated
// REST Assured — Testing duplicate webhook handling
@Test
public void testDuplicateWebhook_processedOnlyOnce() {
    String webhookPayload = """
        {
            "event_id": "evt_abc123",
            "type": "payment.completed",
            "data": {
                "payment_id": "pay_789",
                "amount": 5000,
                "currency": "USD"
            },
            "timestamp": "2026-07-15T10:00:00Z"
        }
    """;
    String signature = computeHmacSignature(webhookPayload, WEBHOOK_SECRET);

    // First delivery
    given()
        .header("Content-Type", "application/json")
        .header("X-Webhook-Signature", signature)
        .body(webhookPayload)
    .when()
        .post("/webhooks/payments")
    .then()
        .statusCode(200)
        .body("processed", equalTo(true));

    // Second delivery — same event_id
    given()
        .header("Content-Type", "application/json")
        .header("X-Webhook-Signature", signature)
        .body(webhookPayload)
    .when()
        .post("/webhooks/payments")
    .then()
        .statusCode(200)
        .body("processed", equalTo(false))
        .body("message", equalTo("Event already processed"));

    // Verify side effect happened only once
    Response orders = given()
        .header("Authorization", "Bearer admin_token")
    .when()
        .get("/api/v1/payments/pay_789/fulfillments")
    .then()
        .extract().response();

    assertEquals(1, orders.jsonPath().getList("fulfillments").size());
}

@Test
public void testDuplicateWebhook_concurrentDelivery() throws Exception {
    String webhookPayload = """
        {
            "event_id": "evt_concurrent_001",
            "type": "order.created",
            "data": {"order_id": "ord_555"}
        }
    """;
    String signature = computeHmacSignature(webhookPayload, WEBHOOK_SECRET);

    ExecutorService executor = Executors.newFixedThreadPool(3);
    List<Future<Integer>> futures = new ArrayList<>();

    for (int i = 0; i < 3; i++) {
        futures.add(executor.submit(() -> given()
            .header("Content-Type", "application/json")
            .header("X-Webhook-Signature", signature)
            .body(webhookPayload)
        .when()
            .post("/webhooks/orders")
        .then()
            .extract().statusCode()));
    }

    List<Integer> statuses = futures.stream()
        .map(f -> { try { return f.get(); } catch (Exception e) { return 500; } })
        .collect(Collectors.toList());

    assertTrue(statuses.stream().allMatch(s -> s == 200),
        "All deliveries should be acknowledged");
}

Q6How do you validate a JSON contract? #

Objective

Demonstrate contract testing approaches including JSON Schema validation, consumer-driven contracts, and structural assertions.

Interview Answer

JSON contract validation ensures that API responses conform to a predefined structure, preventing breaking changes from reaching consumers. There are three levels of validation:

  1. Schema validation — Structure, types, required fields
  2. Semantic validation — Value ranges, enums, patterns
  3. Consumer-driven contracts — Pact/Spring Cloud Contract
// REST Assured + JSON Schema Validator
@Test
public void testResponseMatchesJsonSchema() {
    given()
        .header("Authorization", "Bearer token")
    .when()
        .get("/api/v1/users/123")
    .then()
        .statusCode(200)
        .body(matchesJsonSchemaInClasspath("schemas/user-response.json"));
}

// Inline structural assertions
@Test
public void testUserResponseContract() {
    given()
        .header("Authorization", "Bearer token")
    .when()
        .get("/api/v1/users/123")
    .then()
        .statusCode(200)
        .body("id", notNullValue())
        .body("id", instanceOf(Integer.class))
        .body("email", matchesPattern("^[\\w.]+@[\\w.]+\\.[a-z]{2,}$"))
        .body("role", isIn(Arrays.asList("admin", "user", "moderator")))
        .body("createdAt", matchesPattern("\\d{4}-\\d{2}-\\d{2}T.*Z"))
        .body("address.zipCode", matchesPattern("\\d{5}(-\\d{4})?"))
        .body("$", not(hasKey("password")))
        .body("$", not(hasKey("ssn")));
}

Q13How do you test eventual consistency? #

Objective

Explain testing strategies for systems where data propagation between services is not immediate, requiring time-based assertions.

Interview Answer

Eventual consistency means that after a write, different parts of the system may temporarily return different values until propagation completes. Testing must account for this delay while still catching genuine bugs.

Challenge: Distinguishing between "not yet consistent" (expected) and "will never be consistent" (bug).

Strategy:

  1. Write data to the primary service
  2. Poll the read replica/dependent service with a bounded timeout
  3. Assert consistency is achieved within the SLA
  4. Test that stale reads don't cause incorrect behavior
// REST Assured — Eventual consistency testing
@Test

        .header("Authorization", "Bearer token")
        .body("{\"product\": \"widget\", \"quantity\": 5}")
    .when()
        .post("/api/v1/orders")
    .then()
        .statusCode(201)
        .extract().jsonPath().getString("id");

    // Query the search/analytics service — may take time to propagate
    await()
        .atMost(Duration.ofSeconds(10))
        .pollInterval(Duration.ofMillis(500))
        .untilAsserted(() -> {
            given()
                .header("Authorization", "Bearer token")
                .queryParam("orderId", orderId)
            .when()
                .get("/api/v1/search/orders")
            .then()
                .statusCode(200)
                .body("results.size()", equalTo(1))
                .body("results[0].id", equalTo(orderId));
        });
}

Q28How do you test a webhook signature? #

Objective

Show how to validate that webhook signature verification is correctly implemented to prevent spoofed webhook deliveries.

Interview Answer

Webhook signatures authenticate that a webhook payload genuinely originated from the expected provider and was not tampered with in transit. Testing validates both valid signatures (accepted) and invalid/missing signatures (rejected).

How Webhook Signatures Work:

  1. Provider computes HMAC-SHA256 of the payload using a shared secret
  2. Signature is sent in a header (e.g., X-Webhook-Signature)
  3. Consumer recomputes the signature and compares
  4. If signatures match, the payload is authentic

// Helper method
private String computeHmacSha256(String data, String secret) {
    try {
        Mac mac = Mac.getInstance("HmacSHA256");
        SecretKeySpec keySpec = new SecretKeySpec(secret.getBytes(), "HmacSHA256");
        mac.init(keySpec);
        byte[] hash = mac.doFinal(data.getBytes());
        return Hex.encodeHexString(hash);
    } catch (Exception e) {
        throw new RuntimeException(e);
    }
}

Interview Answer

An API-only defect is one that cannot be reproduced through the UI or caught by unit tests. It typically involves specific request combinations, race conditions, header manipulations, or infrastructure-level issues. Investigation requires a structured approach combining observability tools, traffic analysis, and systematic isolation.

Investigation Framework (RAPID):

  1. Reproduce — Capture the exact failing request
  2. Analyze — Examine logs, traces, and metrics
  3. Pinpoint — Isolate the variable that triggers the defect
  4. Identify — Determine root cause
  5. Document — Record findings and write a regression test
// Step 1: Reproduce — Capture and replay the exact request
@Test
public void reproduceDefect_JIRA_1234() {
    // Exact reproduction from production logs
    Response response = given()
        .header("Content-Type", "application/json")
        .header("Authorization", "Bearer user_token")
        .header("Accept-Language", "fr-FR") // Defect only occurs with French locale
        .header("X-Forwarded-For", "203.0.113.50")
        .body("""
            {
                "amount": 10.50,
                "currency": "EUR",
                "description": "Café résumé — naïve"
            }
        """)
    .when()
        .post("/api/v1/payments")
    .then()
        .extract().response();

    // Log full response for analysis
    System.out.println("Status: " + response.getStatusCode());
    System.out.println("Body: " + response.getBody().asString());
    System.out.println("Headers: " + response.getHeaders());

    // This was returning 500 due to encoding issue with special characters
    assertEquals(201, response.getStatusCode());
}

// Step 2: Analyze — Check correlation ID in distributed tracing
@Test
public void analyzeDefect_traceRequest() {
    String correlationId = "prod-trace-abc123"; // From production logs

    // Query distributed trace
    given()
        .header("Authorization", "Bearer admin_token")
    .when()
        .get("/api/v1/admin/traces/" + correlationId)
    .then()
        .statusCode(200)
        .body("spans.size()", greaterThan(0))
        .body("spans.find { it.service == 'payment-service' }.error", notNullValue());
}

// Step 3: Pinpoint — Isolate the triggering variable
@Test
public void pinpointDefect_isolateVariable() {
    String basePayload = "{\"amount\": 10.50, \"currency\": \"EUR\", \"description\": \"%s\"}";

    // Test with ASCII-only description — works
    given()
        .header("Content-Type", "application/json")
        .header("Authorization", "Bearer token")
        .body(String.format(basePayload, "Normal description"))
    .when()
        .post("/api/v1/payments")
    .then()
        .statusCode(201);

    // Test with UTF-8 special characters — fails
    given()
        .header("Content-Type", "application/json")
        .header("Authorization", "Bearer token")
        .body(String.format(basePayload, "Café résumé"))
    .when()
        .post("/api/v1/payments")
    .then()
        .statusCode(201); // Was returning 500 before fix

    // Test with emoji — also fails
    given()
        .header("Content-Type", "application/json; charset=UTF-8")
        .header("Authorization", "Bearer token")
        .body(String.format(basePayload, "Payment 🎉"))
    .when()
        .post("/api/v1/payments")
    .then()
        .statusCode(201);
}

// Step 4: Identify — Root cause analysis
/*
 * Root Cause: The payment service was using Latin-1 encoding instead of UTF-8
 * when writing to the database. Special characters caused a
 * CharacterEncodingException that wasn't properly caught.
 *
 * Why UI didn't catch it: The UI form stripped special characters before sending.
 * Why unit tests missed it: Unit tests used mock DB that accepted any encoding.
 */

// Step 5: Document — Write regression test
@Test
public void regressionTest_JIRA_1234_utf8InPaymentDescription() {
    String[] testDescriptions = {
        "Café résumé",          // French accented characters
        "naïve señor",          // Spanish characters
        "Ürsprüng",             // German umlauts
        "日本語テスト",            // Japanese
        "Payment 🎉💰",         // Emoji
        "Line1\nLine2",         // Newlines
        "Tab\there",            // Tabs
        "Quote \"test\"",       // Escaped quotes
        "<script>alert(1)</script>"  // XSS attempt (should be stored safely)
    };

    for (String desc : testDescriptions) {
        Response response = given()
            .header("Content-Type", "application/json; charset=UTF-8")
            .header("Authorization", "Bearer token")
            .body("{\"amount\": 10.50, \"currency\": \"EUR\", \"description\": \""
                + desc.replace("\"", "\\\"") + "\"}")
        .when()
            .post("/api/v1/payments")
        .then()
            .statusCode(201)
            .extract().response();

        String paymentId = response.jsonPath().getString("id");

        // Verify stored correctly (round-trip)
        given()
            .header("Authorization", "Bearer token")
        .when()
            .get("/api/v1/payments/" + paymentId)
        .then()
            .body("description", equalTo(desc));
    }
}

Investigation Decision Tree:

API returns unexpected error
├── Can reproduce with curl?
│   ├── YES → Compare headers/body with UI request
│   │   ├── Header difference → Test each header in isolation
│   │   ├── Body difference → Test specific field values
│   │   └── Timing difference → Race condition investigation
│   └── NO → Environment-specific
│       ├── Check server logs for the exact timestamp
│       ├── Check infrastructure (load balancer, DNS, TLS)
│       └── Check if it's intermittent (load/timing dependent)
├── Status code analysis
│   ├── 400 → Request validation issue (check schema)
│   ├── 401/403 → Auth/authz issue (check token, roles)
│   ├── 404 → Routing issue (check path, method)
│   ├── 500 → Server bug (check logs, traces)
│   └── 502/503 → Infrastructure (check upstream services)
└── Works in staging but not prod?
    ├── Configuration difference
    ├── Data difference (prod data has edge cases)
    └── Scale difference (load-related)

Common Mistakes to Avoid

  • Not capturing the full request (headers, body, timing) when reproducing
  • Making changes before fully understanding the root cause
  • Not writing a regression test that specifically covers the edge case
  • Investigating alone without checking observability tools (logs, traces, metrics)

public class ApiTestBase {
    protected static RequestSpecification baseSpec;

    @BeforeAll
    static void setup() {
        baseSpec = new RequestSpecBuilder()
            .setBaseUri("https://api.example.com")
            .setBasePath("/api/v1")
            .addHeader("Content-Type", "application/json")
            .addFilter(new AllureRestAssured())
            .addFilter(new RequestLoggingFilter())
            .addFilter(new ResponseLoggingFilter())
            .build();
    }

    protected Response authenticatedGet(String path, String token) {
        return given()
            .spec(baseSpec)
            .header("Authorization", "Bearer " + token)
        .when()
            .get(path)
        .then()
            .extract().response();
    }
}
