Overview #

System Design for QA is one of the most differentiating skills for senior QA engineers. Unlike developers who design systems for functionality, senior QA engineers must evaluate architectures for testability, observability, failure modes, and resilience. This chapter covers 30 system design scenarios that test your ability to reason about distributed systems, identify failure injection points, and build comprehensive test strategies across every layer.

What Interviewers Evaluate

Dimension What They Look For
Architectural Thinking Can you decompose a system into testable components?
Failure Mode Analysis Can you identify what can go wrong in distributed systems?
Test Strategy Design Can you layer unit, integration, E2E, and chaos tests?
Distributed Systems Knowledge Do you understand CAP theorem, eventual consistency, idempotency?
Tooling Awareness Do you know chaos engineering, contract testing, load testing tools?
Observability Mindset Can you verify systems through metrics, logs, and traces?

Framework for Answering System Design QA Questions

  1. Clarify scope — Ask about scale, SLAs, consistency requirements
  2. Draw architecture — Identify components, data flows, boundaries
  3. Identify failure modes — Network, disk, clock, dependency failures
  4. Layer test strategy — Unit → Integration → Contract → E2E → Chaos
  5. Define observability — Metrics, logs, traces, alerts to verify
  6. Specify tools — Name concrete tools for each testing layer

Q1How would you test a distributed chat system? #

Objective

Demonstrate ability to test real-time, eventually consistent systems with high concurrency, message ordering guarantees, and presence management.

Interview Answer

A distributed chat system must handle real-time message delivery, ordering, presence (online/offline), and persistence across multiple data centers. My testing strategy addresses each layer:

Architecture:

┌──────────┐     ┌──────────────┐     ┌─────────────────┐
│  Client  │────▶│  WebSocket   │────▶│  Message Router  │
│  (App)   │◀────│  Gateway     │◀────│  (Pub/Sub)       │
└──────────┘     └──────────────┘     └────────┬────────┘
                                                │
                       ┌────────────────────────┼────────────────┐
                       │                        │                │
                 ┌─────▼─────┐          ┌──────▼──────┐  ┌─────▼──────┐
                 │  Presence  │          │  Message    │  │  Media     │
                 │  Service   │          │  Store      │  │  Service   │
                 │  (Redis)   │          │  (Cassandra)│  │  (S3+CDN)  │
                 └────────────┘          └─────────────┘  └────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Message serialization, ordering logic, deduplication JUnit, pytest
Integration WebSocket connection lifecycle, pub/sub routing Testcontainers, embedded Redis
Contract API contracts between gateway and router Pact, Spring Cloud Contract
E2E Multi-user conversations, media sharing flows Selenium + WebSocket clients
Chaos Network partitions between data centers Chaos Monkey, Toxiproxy
Load 100K concurrent connections, message throughput Gatling, k6 with WebSocket

Specific Test Cases:

  1. Message ordering — Send 1000 messages rapidly; verify all clients see same order
  2. Delivery guarantee — Kill a gateway mid-delivery; verify message is not lost
  3. Presence accuracy — Disconnect client abruptly; verify presence updates within SLA
  4. Split-brain — Partition two data centers; verify messages reconcile after healing
  5. Duplicate detection — Retry same message with same idempotency key; verify single delivery
  6. Offline sync — Client reconnects after 24h; verify message backfill is complete and ordered

Failure Injection Scenarios:

Scenario: Network partition between DC-East and DC-West
Given: Users A (DC-East) and B (DC-West) are in the same chat room
When: Network partition occurs between data centers
Then: Both users can still send messages to local DC
When: Partition heals
Then: Messages from both sides are merged with correct causal ordering
And: No duplicate messages appear in either client

Observability Testing:

  • Verify message latency metrics (p50, p95, p99) are emitted per hop
  • Confirm dead-letter queue alerts fire when messages fail delivery 3x
  • Validate distributed traces span from client → gateway → router → store
  • Test that presence heartbeat timeouts trigger correct status transitions

Distributed Systems Concepts:

  • Eventual consistency: Messages may arrive out of order across DCs; test reconciliation
  • Idempotency: Clients retry with message IDs; server must deduplicate
  • Vector clocks: Test causal ordering when multiple users edit simultaneously

Common Mistakes

  • Testing only happy-path message delivery without network failures
  • Ignoring message ordering under concurrent writes
  • Not testing reconnection scenarios with message gaps
  • Overlooking presence state becoming stale under partition

Follow-up Questions

  • How would you test end-to-end encryption in this system?
  • What SLA would you set for message delivery latency and how would you verify it?
  • How would you test typing indicators at scale?

Q2How would you test a payment platform? #

Objective

Demonstrate understanding of testing financial systems with strict consistency requirements, idempotency, regulatory compliance, and fraud detection.

Interview Answer

Payment platforms demand the highest testing rigor because failures mean financial loss. The system must be exactly-once, auditable, and compliant with PCI-DSS.

Architecture:

┌──────────┐     ┌──────────────┐     ┌─────────────────┐     ┌──────────────┐
│  Client  │────▶│  API Gateway │────▶│  Payment        │────▶│  Payment     │
│  (App)   │◀────│  (Auth+Rate) │◀────│  Orchestrator   │◀────│  Processor   │
└──────────┘     └──────────────┘     └────────┬────────┘     │  (Stripe/    │
                                                │              │   Adyen)     │
                       ┌────────────────────────┼──────┐       └──────────────┘
                       │                        │      │
                 ┌─────▼─────┐          ┌──────▼──┐  ┌▼───────────┐
                 │  Fraud    │          │  Ledger │  │  Webhook    │
                 │  Engine   │          │  (ACID) │  │  Handler    │
                 │  (ML+Rules)│         │  (PG)   │  │  (Idempotent)│
                 └────────────┘          └─────────┘  └─────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Amount calculations, currency conversion, fee logic JUnit with BigDecimal assertions
Integration Ledger double-entry bookkeeping, fraud rule evaluation Testcontainers (PostgreSQL)
Contract Payment processor API contract stability Pact, WireMock
E2E Full payment flow: authorize → capture → settle Stripe test mode, sandbox environments
Chaos Processor timeout mid-transaction, DB failover Toxiproxy, LitmusChaos
Load Black Friday spike: 10x normal transaction volume Gatling, Locust

Specific Test Cases:

  1. Idempotency — Submit same payment request twice with same key; verify single charge
  2. Double-entry ledger — After every transaction, verify debits = credits
  3. Partial failure — Processor approves but DB write fails; verify reconciliation
  4. Webhook replay — Send same webhook 5 times; verify single state transition
  5. Currency precision — Test JPY (0 decimals), USD (2), BHD (3) all calculate correctly
  6. Timeout handling — Processor takes 30s to respond; verify no duplicate charges
  7. Refund integrity — Refund amount cannot exceed original charge amount
  8. PCI compliance — Verify card numbers never appear in logs, metrics, or error messages

Failure Injection Scenarios:

Scenario: Database failure after processor approval
Given: Customer submits $100 payment
And: Payment processor successfully authorizes the charge
When: Database connection drops before ledger write
Then: System queues a reconciliation event
And: No duplicate charge is created when DB recovers
And: Customer sees "processing" status (not "failed")
And: Reconciliation job matches processor records with ledger within 5 minutes

Observability Testing:

  • Verify payment state machine transitions emit metrics (authorized, captured, failed, refunded)
  • Confirm alerting fires when settlement mismatch exceeds $0.01
  • Test that distributed traces include processor response times
  • Validate PCI audit logs record all access to cardholder data

Distributed Systems Concepts:

  • ACID transactions: Ledger must be strongly consistent; test isolation levels
  • Idempotency keys: Every mutation must be safely retryable
  • Saga pattern: Multi-step payments use compensating transactions; test rollback paths
  • Exactly-once semantics: Webhooks + retries must not create duplicate records

Common Mistakes

  • Using floating-point arithmetic for monetary calculations
  • Not testing the unhappy path where processor approves but internal state fails
  • Ignoring currency-specific decimal handling
  • Testing only with small amounts (missing overflow/precision issues at scale)

Follow-up Questions

  • How would you test a payment system's compliance with PCI-DSS?
  • How would you verify that no sensitive card data leaks into logs?
  • How would you test a multi-currency payment split?

Q3How would you test a notification service? #

Objective

Demonstrate ability to test multi-channel delivery systems with rate limiting, user preferences, deduplication, and delivery guarantees.

Interview Answer

Notification services must deliver messages across multiple channels (push, email, SMS, in-app) while respecting user preferences, avoiding spam, and guaranteeing delivery.

│  Event       │────▶│  Notification│────▶│  Channel Router  │
│  Producers   │     │  Aggregator  │     │  (Preferences)   │
│  (Services)  │     │  (Dedup+     │     └────────┬─────────┘
└──────────────┘     │   Throttle)  │              │
                     └──────────────┘     ┌────────┼────────────────┐
                                          │        │                │
                                    ┌─────▼──┐ ┌──▼────────┐ ┌────▼─────┐
                                    │  Push  │ │  Email     │ │  SMS     │
                                    │  (FCM/ │ │  (SES/     │ │  (Twilio/│
                                    │  APNs) │ │  SendGrid) │ │  SNS)    │
                                    └────────┘ └────────────┘ └──────────┘
                                          │        │                │
                                    ┌─────▼────────▼────────────────▼─────┐
                                    │       Delivery Status Tracker        │
                                    │       (DynamoDB + Dead Letter Q)     │
                                    └─────────────────────────────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Template rendering, preference matching, throttle logic JUnit, pytest
Integration Channel routing with real preferences DB Testcontainers
Contract Provider API contracts (FCM, SES, Twilio) Pact, WireMock
E2E User receives notification across all subscribed channels Mailhog, mock push server
Chaos Push provider outage, email bounce storms Toxiproxy, Gremlin
Load 1M notifications/minute burst (Black Friday alerts) k6, Locust

Specific Test Cases:

  1. Preference honoring — User opts out of email; verify no email sent, other channels active
  2. Deduplication — Same event fires twice within 5 minutes; only one notification delivered
  3. Rate limiting — User would receive 50 notifications/hour; verify batching/throttling
  4. Fallback channels — Push delivery fails; verify SMS fallback within configured timeout
  5. Template rendering — Test with special characters, long names, missing variables
  6. Quiet hours — Notification arrives at 2 AM user-local-time; verify held until morning
  7. Delivery tracking — Verify bounce, open, click events update delivery status correctly

Failure Injection Scenarios:

Scenario: Push notification provider outage
Given: FCM is unreachable (connection timeout)
When: 10,000 push notifications are queued
Then: System retries with exponential backoff (1s, 2s, 4s, 8s)
And: After 3 retries, messages move to dead-letter queue
And: Alert fires for "push_delivery_failure_rate > 50%"
And: Fallback to in-app notification is triggered per configuration

Observability Testing:

  • Verify delivery rate metrics per channel (sent, delivered, bounced, opened)
  • Confirm latency histograms from event ingestion to delivery per channel
  • Test that dead-letter queue depth alerts fire at configured threshold
  • Validate audit trail records who received what notification and when

Distributed Systems Concepts:

  • At-least-once delivery: Notifications may retry; test deduplication at client
  • Eventual consistency: Preference updates may not apply immediately to in-flight messages
  • Backpressure: Test system behavior when downstream providers are slow

Common Mistakes

  • Not testing timezone-aware quiet hours across DST transitions
  • Ignoring notification fatigue and rate limiting logic
  • Testing providers in isolation without end-to-end delivery verification
  • Not verifying idempotency when events are replayed from message queues

Follow-up Questions

  • How would you test notification priority levels (critical vs. marketing)?
  • How would you verify GDPR consent is checked before sending?
  • How would you load test push notifications without hitting real FCM/APNs?

Q4How would you test a file-storage service? #

Objective

Demonstrate ability to test a system with large binary payloads, eventual consistency, access control, and data durability requirements.

Interview Answer

File storage services handle uploads, downloads, metadata management, and access control at scale. Key challenges include large file handling, concurrent access, and durability guarantees.

Architecture:

┌──────────┐     ┌──────────────┐     ┌─────────────────┐     ┌──────────────┐
│  Client  │────▶│  API Gateway │────▶│  Upload Service  │────▶│  Object      │
│          │◀────│  (Auth+      │◀────│  (Chunked/       │     │  Store       │
└──────────┘     │   Presigned) │     │   Multipart)     │     │  (S3/GCS)    │
                 └──────────────┘     └────────┬─────────┘     └──────────────┘
                                               │
                       ┌───────────────────────┼──────────────┐
                       │                       │              │
                 ┌─────▼─────┐         ┌──────▼──────┐ ┌────▼──────────┐
                 │  Metadata │         │  Virus      │ │  Thumbnail    │
                 │  Service  │         │  Scanner    │ │  Generator    │
                 │  (PostgreSQL)│      │  (ClamAV)   │ │  (Lambda)     │
                 └────────────┘        └─────────────┘ └───────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Chunk assembly, hash verification, ACL evaluation JUnit, pytest
Integration Multipart upload with real object store LocalStack, MinIO
Contract Pre-signed URL generation, metadata API Pact
E2E Upload → scan → thumbnail → share → download Cypress, Playwright
Chaos Storage node failure mid-upload, network timeouts Toxiproxy, Chaos Mesh
Load 10K concurrent uploads of 1GB files k6, custom upload clients

Specific Test Cases:

  1. Chunked upload resume — Upload 80% of a 5GB file, disconnect, resume; verify completion
  2. Concurrent access — Two users upload same filename simultaneously; verify no data corruption
  3. Access control — Shared link expires after 24h; verify 403 after expiry
  4. Virus scanning — Upload EICAR test file; verify quarantine and user notification
  5. Storage quotas — User at 99% quota; verify appropriate error and no partial writes
  6. Content-type validation — Upload .exe renamed to .jpg; verify server-side type detection
  7. Cross-region replication — Upload in US-East; verify accessible from EU-West within SLA
  8. Integrity verification — Download file; verify SHA-256 matches upload checksum

Failure Injection Scenarios:

Scenario: Storage backend failure during multipart upload
Given: User is uploading a 2GB file in 10MB chunks
And: 150 of 200 chunks have been stored successfully
When: Object store returns 503 for subsequent chunk uploads
Then: Client retries failed chunks with exponential backoff
And: Successfully uploaded chunks are not re-uploaded (resume from last)
And: If failure persists > 1 hour, incomplete upload is cleaned up
And: User receives actionable error with resume capability

Observability Testing:

  • Verify upload/download latency percentiles per file size bucket
  • Confirm storage utilization metrics per tenant align with actual usage
  • Test that failed virus scan alerts include file hash and upload source
  • Validate that orphaned chunk cleanup job metrics report cleaned vs. skipped

Distributed Systems Concepts:

  • Eventual consistency: Newly uploaded files may not be immediately listable (S3 model)
  • Idempotency: Re-uploading same content with same key should be safe
  • CAP trade-off: Prefer availability for reads, consistency for metadata updates

Common Mistakes

  • Testing only with small files (missing chunked upload edge cases)
  • Not testing concurrent uploads to the same path
  • Ignoring cleanup of failed/incomplete uploads
  • Not verifying that deleted files are actually purged from storage (not just metadata)

Follow-up Questions

  • How would you test file versioning and rollback?
  • How would you verify data durability (11 9's) in testing?
  • How would you test file sharing permissions across organizational boundaries?

Demonstrate ability to test systems with eventual consistency between source-of-truth and index, relevance ranking, and performance under load.

Search systems have a fundamental testing challenge: the index is eventually consistent with the source data, relevance is subjective, and performance degrades non-linearly with data volume.

                                            ┌──────▼──────────┐
┌──────────┐     ┌──────────────┐          │  Search Index    │
│  Client  │────▶│  Search API  │─────────▶│  (Elasticsearch/ │
│          │◀────│  (Query      │◀─────────│   OpenSearch)    │
└──────────┘     │   Parser)    │          └─────────────────┘

Layer What to Test Tools
Unit Query parsing, tokenization, filter logic JUnit, pytest
Integration CDC pipeline with real Elasticsearch Testcontainers (ES + PG)

E2E Create document → wait → search → find Playwright, REST clients
Chaos Index node failure, CDC lag spike Chaos Mesh, Toxiproxy

Specific Test Cases:

  1. Indexing lag — Create document; measure time until searchable (SLA: <5s)
  2. Relevance regression — Maintain golden queries with expected top-5 results; alert on drift
  3. Partial matching — Search "javascrip" finds "JavaScript" (typo tolerance)
  4. Faceted search — Filter by category + price range; verify counts match source DB
  5. Index rebuild — Trigger full reindex; verify zero-downtime with alias swap
  6. Deleted content — Delete document from source; verify removed from index within SLA
  7. Multi-language — Search in Chinese, Arabic, German; verify tokenization correctness
  8. Permission filtering — User A cannot see User B's private documents in results

Failure Injection Scenarios:

Scenario: CDC pipeline lag causes stale search results
Given: Normal indexing lag is <2 seconds
When: Database experiences high write throughput (10x normal)
And: CDC pipeline consumer lag exceeds 60 seconds
Then: Search results show stale data (acceptable within SLA)
And: Lag metric alert fires at 30s threshold
And: System does NOT serve completely empty results
And: When lag recovers, all documents eventually appear in index

Observability Testing:

  • Verify indexing lag metric (time between DB write and index availability)
  • Confirm query latency percentiles (p50 < 100ms, p99 < 500ms)
  • Test relevance metrics (NDCG, MRR) are computed and tracked over time
  • Validate that index size and shard health metrics are emitted

Distributed Systems Concepts:

  • Eventual consistency: Index always lags source; test acceptable staleness windows
  • CAP theorem: Search favors availability; stale results preferred over no results
  • Idempotency: Re-indexing same document must be safe (upsert semantics)

Common Mistakes

  • Only testing search with small datasets (relevance changes at scale)
  • Not establishing relevance baselines before making ranking changes
  • Ignoring the indexing lag in E2E tests (flaky tests from race conditions)
  • Testing exact match only, missing fuzzy/partial/synonym scenarios

Follow-up Questions

  • How would you implement relevance regression testing in CI/CD?
  • How would you test search personalization without bias?
  • How would you verify that search respects real-time permission changes?

  2. Model freshness — Train new model; verify A/B framework routes traffic correctly
  3. Diversity — Recommendations don't show 10 items from same category (filter bubble)
  4. Exclusion rules — Previously purchased items don't appear in recommendations
  5. Feature staleness — Feature store returns stale data; verify graceful degradation
  6. Bias detection — Verify recommendations don't discriminate by protected attributes
  7. Feedback loop — Click on recommendation; verify it influences future results within SLA

Scenario: Model serving latency spike
Given: Normal model inference takes 20ms
When: Model serving latency exceeds 200ms (10x degradation)
Then: System falls back to pre-computed recommendations (cache)
And: Fallback metric increments
And: User sees recommendations within 300ms total (SLA maintained)
And: When model recovers, system returns to real-time inference

  • Verify CTR (click-through rate) metrics per model version
  • Confirm feature freshness metrics (age of features used in inference)
  • Test A/B experiment metrics are correctly attributed to variants
  • Validate model inference latency and error rate dashboards

Distributed Systems Concepts:

  • Eventual consistency: User activity may not be reflected immediately in features
  • Idempotency: Same request with same features must return same recommendations
  • CAP trade-off: Prefer availability; stale recommendations over no recommendations

Common Mistakes

  • Testing recommendations only for accuracy, ignoring diversity and fairness
  • Not verifying that A/B bucketing is deterministic and consistent per user
  • Ignoring cold-start scenarios in test plans
  • Not establishing offline evaluation metrics before online A/B testing

Follow-up Questions

  • How would you detect and test for recommendation bias?
  • How would you verify that model retraining doesn't degrade quality?
  • How would you test recommendation explanations ("Because you watched...")?

  • Validate that error rate comparison (before vs after rollback) is available

Distributed Systems Concepts:

  • Backward compatibility: New code must work with old data and vice versa
  • Blue-green deployments: Keep previous version running for instant rollback
  • Expand-contract pattern: Database changes that work with both old and new code
  • Idempotent migrations: Running migration multiple times is safe

Common Mistakes

  • Never testing rollback (only testing forward deployment)
  • Not testing data created during v2 is compatible with v1 code
  • Ignoring database schema rollback (only rolling back application code)
  • Not testing rollback speed under production-like conditions

Follow-up Questions

  • How would you test rollback for a database change that's not reversible (data transformation)?
  • How would you test rollback in a microservices architecture with version dependencies?
  • What's your strategy when rollback itself fails?

Q28How would you test schema evolution? #

Objective

Demonstrate ability to test database and API schema changes that maintain backward compatibility, data integrity, and zero-downtime deployments.

Interview Answer

Schema evolution testing verifies that structural changes to databases, APIs, or message formats don't break existing consumers, lose data, or require downtime.

Architecture:

┌────────────────────────────────────────────────────────────────┐
│                    Schema Evolution Patterns                     │
│                                                                 │
│  Database (Expand-Contract):                                    │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────┐       │
│  │ Phase 1: │────▶│ Phase 2:     │────▶│ Phase 3:     │       │
│  │ ADD new  │     │ Migrate data │     │ DROP old     │       │
│  │ column   │     │ (backfill)   │     │ column       │       │
│  └──────────┘     └──────────────┘     └──────────────┘       │
│                                                                 │
│  API Versioning:                                                │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────┐       │
│  │ v1: name │     │ v2: first,   │     │ v1 deprecated│       │
│  │          │     │     last     │     │ v2 primary   │       │
│  └──────────┘     └──────────────┘     └──────────────┘       │
│                                                                 │
│  Event Schema (Forward Compatibility):                          │
│  ┌──────────┐     ┌──────────────┐                             │
│  │ v1 event │     │ v2 event     │  v1 consumers ignore       │
│  │ {a, b}   │     │ {a, b, c}    │  unknown fields            │
│  └──────────┘     └──────────────┘                             │
└────────────────────────────────────────────────────────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Data transformation logic, default value handling JUnit, pytest
Integration Migration execution on production-like data volumes Flyway, Liquibase, pgTAP
Contract Old clients work with new schema (backward compat) Pact, Avro schema registry
E2E Full deployment with migration under traffic Staging environment
Load Migration performance on billion-row tables Custom benchmarks
Compatibility N-1 version reads N version data (forward compat) Version matrix testing

Specific Test Cases:

  1. Additive change — Add nullable column; verify old code ignores it, new code uses it
  2. Column rename — Rename via expand-contract; verify both old and new names work during transition
  3. Type change — Change string → enum; verify data migration preserves all values
  4. Backfill correctness — Backfill 10M rows; verify all transformed correctly
  5. Concurrent access — Run migration while application processes requests; verify no errors
  6. Rollback migration — Run down migration; verify schema returns to previous state
  7. Schema registry — Publish breaking change; verify registry rejects incompatible schema
  8. Consumer compatibility — New event schema; verify all consumers handle gracefully

Failure Injection Scenarios:

Scenario: Long-running migration on large table
Given: Table has 500M rows and needs a new indexed column
And: Application is serving production traffic
When: ALTER TABLE ADD COLUMN executes (non-blocking in PG)
And: Background job backfills values for new column (2 hours)
Then: No read/write locks acquired on the table during migration
And: Application continues serving requests with no latency increase
And: New column has NULL values until backfilled (handled by code)
And: After backfill, both old code (ignores column) and new code (uses column) work
And: NOT NULL constraint added only after 100% backfill verified

Observability Testing:

  • Verify migration duration metrics per migration step
  • Confirm table lock wait metrics during schema changes
  • Test that schema version tracking clearly shows current state
  • Validate that incompatible schema changes are blocked by CI/CD checks

Distributed Systems Concepts:

  • Backward compatibility: New schema must not break old consumers
  • Forward compatibility: Old schema consumers must handle new schema gracefully
  • Expand-contract: Safe pattern for non-breaking schema changes
  • Eventual migration: Large backfills are eventually consistent; new code handles both states

Common Mistakes

  • Testing migrations on empty databases (missing production data volume effects)
  • Not testing the transition period when both old and new code run simultaneously
  • Assuming all column additions are non-breaking (NOT NULL without default breaks)
  • Not testing migration rollback (down migration)

Follow-up Questions

  • How would you test a schema migration on a 1TB table with zero downtime?
  • How would you handle schema evolution for event-driven systems with Avro/Protobuf?
  • How would you test that old API versions are correctly sunset?

Q29How would you test GDPR-style deletion? #

Objective

Demonstrate ability to verify that personal data deletion is complete, irreversible, and compliant across all systems that hold the data.

Interview Answer

GDPR "Right to Erasure" requires that all personal data for a subject is deleted or anonymized across ALL systems within 30 days. Testing must verify completeness, irreversibility, and that no data lingers in backups, caches, or logs.

Architecture:

┌──────────────┐     ┌──────────────┐     ┌─────────────────┐
│  Deletion    │────▶│  Orchestrator│────▶│  System A (DB)   │
│  Request     │     │  (Saga       │     │  → DELETE user   │
│  (Subject    │     │   Pattern)   │     └─────────────────┘
│   Access     │     │              │     ┌─────────────────┐
│   Request)   │     │              │────▶│  System B (S3)   │
└──────────────┘     │              │     │  → DELETE files  │
                     │              │     └─────────────────┘
                     │              │     ┌─────────────────┐
                     │              │────▶│  System C (Elastic)│
                     │              │     │  → DELETE docs   │
                     │              │     └─────────────────┘
                     │              │     ┌─────────────────┐
                     │              │────▶│  System D (Logs) │
                     └──────────────┘     │  → ANONYMIZE     │
                            │             └─────────────────┘
                     ┌──────▼───────┐
                     │  Deletion    │
                     │  Verification│
                     │  Certificate │
                     └──────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Anonymization logic, field-level deletion rules JUnit, pytest
Integration Deletion across each data store Testcontainers, LocalStack
Contract Deletion API request/response format OpenAPI validation
E2E Full deletion request → verification across all systems Custom framework
Compliance Verify data cannot be recovered after deletion Audit scripts
Timing Deletion completes within 30-day GDPR window SLA monitoring

Specific Test Cases:

  1. Complete deletion — Delete user; search all systems; verify zero PII found
  2. Backup handling — Data exists in backup; verify excluded on next restore
  3. Cache purge — Data was cached; verify removed from all cache layers
  4. Log anonymization — User's actions in logs; verify PII anonymized (not deleted)
  5. Third-party propagation — Data shared with Stripe, analytics; verify deletion propagated
  6. Derived data — ML model trained on user data; verify model retrained or data removed
  7. Partial deletion — Retain legally required data (invoices); delete everything else
  8. Verification certificate — After deletion, generate proof of completion for audit

Failure Injection Scenarios:

Scenario: Deletion fails for one of five systems
Given: User requests deletion of all personal data
And: Data exists in: PostgreSQL, Elasticsearch, S3, Redis, Analytics
When: Deletion orchestrator begins saga across all systems
And: Elasticsearch delete fails (cluster unhealthy)
Then: Successful deletions (PG, S3, Redis, Analytics) are NOT rolled back
And: Elasticsearch deletion is queued for retry
And: Deletion status shows "partial - retrying" with failed system listed
And: Alert fires for "deletion_incomplete" with 24h SLA for resolution
And: After ES recovery, deletion completes and certificate is generated
And: Total time does not exceed 30-day GDPR deadline

Observability Testing:

  • Verify deletion request status tracking (pending, in-progress, partial, complete)
  • Confirm per-system deletion latency metrics
  • Test that overdue deletion alerts fire before GDPR deadline
  • Validate deletion certificate generation includes all systems verified

Distributed Systems Concepts:

  • Saga pattern: Coordinate deletion across multiple services without distributed transactions
  • Eventual deletion: Data may persist temporarily in replicas; verify final state
  • Tombstones: Soft-delete markers that prevent data from reappearing
  • Right to be forgotten vs data retention: Conflict resolution between deletion and legal hold

Common Mistakes

  • Only testing deletion in primary database, ignoring replicas, caches, logs, and backups
  • Not testing that deleted data doesn't reappear after backup restoration
  • Ignoring third-party systems that hold copies of the data
  • Not generating auditable proof that deletion was complete

Follow-up Questions

  • How would you test deletion when data is embedded in aggregate/analytics tables?
  • How would you verify deletion across 50+ microservices?
  • How would you test the conflict between GDPR deletion and legal hold requirements?

Q30How would you test a production canary? #

Objective

Demonstrate ability to verify that canary deployment mechanisms correctly detect problems, route traffic appropriately, and auto-rollback when quality degrades.

Interview Answer

Canary testing verifies that the progressive deployment mechanism itself works correctly — that it detects bad deployments, limits blast radius, and rolls back automatically before users are significantly impacted.

Architecture:

┌─────────────────────────────────────────────────────────────┐
│                    Canary Deployment Pipeline                 │
│                                                              │
│  ┌──────────┐    ┌───────────────────────────────────┐      │
│  │  Load    │    │  Production Fleet                  │      │
│  │  Balancer│    │                                    │      │
│  │          │──▶ │  ┌─────────────────────────────┐  │      │
│  │  Traffic │    │  │  Stable (v2.0) — 95% traffic│  │      │
│  │  Split   │    │  │  [Pod][Pod][Pod][Pod][Pod]  │  │      │
│  │          │    │  └─────────────────────────────┘  │      │
│  │          │──▶ │  ┌─────────────────────────────┐  │      │
│  │          │    │  │  Canary (v2.1) — 5% traffic │  │      │
│  │          │    │  │  [Pod]                       │  │      │
│  └──────────┘    │  └─────────────────────────────┘  │      │
│                  └───────────────────────────────────┘      │
│                                                              │
│  ┌──────────────────────────────────────────────────┐       │
│  │  Canary Analysis                                  │       │
│  │  Compare: error_rate(canary) vs error_rate(stable)│       │
│  │  Compare: latency(canary) vs latency(stable)      │       │
│  │  Compare: saturation(canary) vs saturation(stable)│       │
│  │  Decision: PROMOTE | ROLLBACK | CONTINUE          │       │
│  └──────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────┘

Test Strategy by Layer:

Layer What to Test Tools
Unit Canary analysis statistical comparison logic JUnit, pytest
Integration Traffic splitting accuracy, metric collection per variant Kubernetes + Istio
Contract Canary analysis report format Schema validation
E2E Deploy bad canary → detect → auto-rollback → verify Flagger, Argo Rollouts
Statistical False positive/negative rates of canary analysis Historical data replay
Load Canary behavior under high traffic (metric accuracy) k6, Locust

Specific Test Cases:

  1. Traffic splitting accuracy — Set 5% canary; verify actual traffic is 4.5-5.5%
  2. Bad canary detection — Deploy version with 10x error rate; verify auto-rollback
  3. Slow canary detection — Deploy version with 2x latency; verify detection within SLA
  4. Good canary promotion — Deploy healthy version; verify auto-promotion to 100%
  5. Metric isolation — Canary metrics don't pollute stable metrics (separate labels)
  6. Sticky sessions — User hits canary; subsequent requests stay on canary (consistency)
  7. Rollback speed — From detection to full rollback; verify <2 minutes
  8. Manual override — Operator forces rollback; verify immediate effect

Failure Injection Scenarios:

Scenario: Canary deploys version with memory leak
Given: Canary is deployed with 5% traffic
And: New version has a slow memory leak (grows 10MB/hour)
And: Analysis window is 30 minutes
When: After 15 minutes, canary pod's memory usage grows abnormally
Then: Saturation metric (memory utilization) diverges from stable
And: Canary analysis detects divergence in resource utilization
And: If configured for auto-rollback on resource anomaly: rollback fires
And: If not configured: alert fires for manual investigation
And: Pod doesn't OOM during analysis window (memory limit protects)
And: After rollback, no user impact from the memory-leaking version

Observability Testing:

  • Verify per-variant metrics are correctly labeled (canary vs stable)
  • Confirm canary analysis decision metrics (promote/rollback/continue counts)
  • Test that canary duration metrics track time from deploy to decision
  • Validate blast radius metrics (what % of users were affected before rollback)

Distributed Systems Concepts:

  • Statistical significance: Canary analysis needs enough traffic for valid comparison
  • Blast radius control: Limit exposure to protect most users from bad deploys
  • Observability: Canary relies on accurate, real-time metrics per variant
  • Automated decision-making: Machine-driven rollback faster than human response

Common Mistakes

  • Not testing the canary analysis logic itself (trusting it blindly)
  • Setting canary traffic too low for statistical significance
  • Not testing slow-burn issues that only manifest after analysis window
  • Not verifying that rollback actually removes ALL canary pods

Follow-up Questions

  • How would you determine the right traffic percentage and analysis duration for a canary?
  • How would you test canary deployments for async services (no request traffic)?
  • How would you test canary analysis when baseline metrics are noisy?
